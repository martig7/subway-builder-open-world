# Railyard loader feasibility for NEC distribution

Research date: 2026-09-01  
Scope: read-only inspection of the installed Railyard 0.2.10 executable and state, Railyard-generated Subway Builder mods, the installed Subway Builder 1.6.0 bundle, the NEC source/build artifacts, and the first-party Railyard repositories.

## Verdict

**Railyard can plausibly remove the PowerShell step, but not by letting the NEC renderer mod “register” its existing tile directory at runtime.** The practical integration is to distribute the NEC runtime as a normal Railyard mod and distribute each NEC city/tile package through Railyard's map-install pipeline. Railyard itself then owns PMTiles serving and city-data placement when the user launches Subway Builder through Railyard.

That path is technically credible but is not drop-in today. The current NEC build is a 34-city open-world consumer that hard-codes its own PMTiles service at port 8799, while Railyard generates a closed-over loader configuration with its own dynamic port. There is no installed public handshake/API for a second mod to append places to the generated loader, discover its port, start Railyard, or invoke Railyard's installer.

Recommended disposition: **pursue a Railyard-native distribution in coordination with the Railyard maintainers**, retaining the current standalone PowerShell server only as a developer/manual fallback. A maintainer-side “map pack/collection” or dependency mechanism is the main product gap if the desired user experience is genuinely one click rather than 34 map installs plus one mod install.

The local Railyard log proves the normal remote-map lifecycle: resolve a map's custom/GitHub version source, download a ZIP, extract it, report the extracted city code, then mark the asset installed (`C:\Users\darkd\AppData\Roaming\railyard\railyard.log`, for example lines 800–812). Installed artifacts prove where extraction lands:

- PMTiles archives are stored as `C:\Users\darkd\AppData\Roaming\railyard\tiles\<CODE>.pmtiles` (with optional `<CODE>_foundations.pmtiles`).
- Native city data is placed in `C:\Users\darkd\AppData\Roaming\metro-maker4\cities\data\<CODE>\` and marked with `.railyard_asset`.
- Arbitrary map-side companion content is preserved; the installed `KHS` package includes `.railyard_map`, compressed native data, and `driving_paths.json.gz` in addition to its separately stored PMTiles archive.

The installed executable is `C:\Program Files\Subway Builder Modded\Railyard\railyard.exe` (version 0.2.10). Its embedded Go symbols provide primary evidence of the privileged backend surface:

- `main.(*App).generateMod`, `main.(*App).startPMTilesServer`, and `main.(*App).LaunchGame`
- `railyard/internal/downloader.(*Downloader).installMapNow`, `extractMap`, `getMapDataPath`, `getMapTilePath`, and `ImportAsset`
- `railyard/internal/downloader.(*Downloader).installModNow` and `extractMod`

The same executable embeds `github.com/protomaps/go-pmtiles/pmtiles` and a `main.pmtilesProxyHandler`. This proves that Railyard has its own native PMTiles server and import/install machinery. It does **not** prove that those Go methods are callable from a Subway Builder renderer mod; they are bound to Railyard's own Wails frontend.

The executable also contains a local-map import path (`OpenImportAssetDialog`, `ValidateImportedMapArchives`, `ImportAsset`, and `LocalMaps`). That is useful for testing without PowerShell: users can import Railyard-compatible map archives through Railyard. Registry publication remains the better release path because local import is still a manual UI operation.

## Subway Builder mod lifecycle and process boundary

Subway Builder discovers and loads ordinary mods independently of Railyard. The active 1.6.0 renderer waits for `SubwayBuilderAPI`, calls `window.electron.scanMods()`, filters enabled/error-free mods, requests each script, and executes them in sequence ([renderer bundle](<C:/Users/darkd/AppData/Local/Temp/nec-railyard-research-asar/dist/renderer/public/index-BCLhXOq-.js#L225263>), [renderer bundle](<C:/Users/darkd/AppData/Local/Temp/nec-railyard-research-asar/dist/renderer/public/index-BCLhXOq-.js#L225280>), [renderer bundle](<C:/Users/darkd/AppData/Local/Temp/nec-railyard-research-asar/dist/renderer/public/index-BCLhXOq-.js#L225300>)). Script execution is a strict IIFE constructed with `new Function`, in the renderer world ([renderer bundle](<C:/Users/darkd/AppData/Local/Temp/nec-railyard-research-asar/dist/renderer/public/index-BCLhXOq-.js#L220106>)).

This gives NEC access to browser APIs and `SubwayBuilderAPI`, but not Node's `child_process`. The installed preload exposes mod scanning/script loading/storage and city-data helpers, while its generic secure invoke path checks a small `MOD_ALLOWED_CHANNELS` set and rejects unlisted channels ([preload](<C:/Users/darkd/AppData/Local/Temp/nec-railyard-research-asar/dist/preload/preload.js#L41>), [preload](<C:/Users/darkd/AppData/Local/Temp/nec-railyard-research-asar/dist/preload/preload.js#L49>), [preload](<C:/Users/darkd/AppData/Local/Temp/nec-railyard-research-asar/dist/preload/preload.js#L206>)). No exposed API starts an arbitrary process, invokes PowerShell, calls Railyard's backend, or writes arbitrary external files.

Therefore:

- **Proven impossible through the installed public bridge:** have the NEC renderer script spawn its current PowerShell service or invoke a Railyard installer.
- **Proven available to Railyard itself:** copy/extract map and mod payloads and run a native PMTiles server when Railyard owns the launch lifecycle.
- **Not found:** package-level post-install, executable, service, or shell hooks. Across the locally cloned Railyard registry, all map and mod manifest keys were enumerated; none used `script`, `install`, `postinstall`, `executable`, `command`, `service`, `process`, `powershell`, or `shell` fields.

## NEC compatibility blockers

### 1. NEC currently overrides Railyard's server

The NEC consumer hard-codes `DEFAULT_TILE_BASE = http://127.0.0.1:8799` and creates URLs of the form `/<tileId>/{z}/{x}/{y}.mvt` ([city-registration.js](../../prototype/nec-corridor/mod/src/city-registration.js#L3), [city-registration.js](../../prototype/nec-corridor/mod/src/city-registration.js#L18)). Even when a city already exists, `registerPilotCities` calls `refreshPilotCityBindings` for every city, overwriting tile/data bindings with the 8799 service ([city-registration.js](../../prototype/nec-corridor/mod/src/city-registration.js#L147), [city-registration.js](../../prototype/nec-corridor/mod/src/city-registration.js#L155)).

A Railyard build must instead let the generated Railyard loader own tile URLs and native data paths, or obtain a supported server-base handshake from Railyard. The Railyard base URL is currently private to its generated closure.

### 2. NEC is 34 Railyard-sized maps, not one map listing

The catalog explicitly requires 34 selected tiles ([tile-catalog.js](../../prototype/nec-corridor/mod/src/tile-catalog.js#L21)). Each becomes a distinct Subway Builder city definition and data binding ([city-registration.js](../../prototype/nec-corridor/mod/src/city-registration.js#L6), [city-registration.js](../../prototype/nec-corridor/mod/src/city-registration.js#L31)). Railyard's installed state and registry manifests are one city code per map asset. No map-pack/collection field was found in the installed registry schema.

Without a Railyard enhancement, the faithful mapping is therefore **34 Railyard map assets plus one NEC runtime mod**. Packaging all 34 city folders inside a normal mod ZIP would not place them under Subway Builder's `cities/data` tree, and Railyard mod manifests provide no install-script hook to do so.

### 3. The current archives are not yet Railyard map archives

The NEC installer expects seven files per tile and directly copies them into `cities/data/<tileId>` ([install-mod.mjs](../../prototype/nec-corridor/mod/scripts/install-mod.mjs#L10), [install-mod.mjs](../../prototype/nec-corridor/mod/scripts/install-mod.mjs#L67)). It then starts the bundled PowerShell server ([install-mod.mjs](../../prototype/nec-corridor/mod/scripts/install-mod.mjs#L79)). Railyard packages instead need per-map metadata/config and update/registry metadata in the format Railyard validates and installs.

The build should emit one Railyard-compatible ZIP per selected city code, plus the separately published NEC mod ZIP. The current world package manifest can remain build metadata, but it is not a Railyard registry manifest.

### 4. Load ordering and duplicate city registration need an explicit contract

The game loads enabled mods sequentially, but the installed evidence does not establish a dependency order between `com.railyard.maploader` and the NEC mod. If NEC runs first it may register the 34 cities before Railyard; if Railyard runs first, NEC currently sees existing cities but still replaces their bindings. A robust integration needs one of:

- a Railyard-supported loader-ready event/API;
- an agreed mod dependency/load-order mechanism; or
- an NEC “Railyard mode” that waits for all expected codes and never replaces Railyard-owned tile/data URLs.

Using `window.fetch.__railyardPathShim` as detection is technically possible because the generated loader marks its shim ([index.js](<C:/Users/darkd/AppData/Roaming/metro-maker4/mods/mapLoader/index.js#L97>)), but it is an internal implementation detail and not a suitable long-term distribution contract.

### 5. Direct game launches remain a distinct mode

Railyard's server is owned by the Railyard application. A mod cannot assume it exists when Subway Builder is launched directly. A Railyard-native release should either require “Launch through Railyard” and present a clear in-game diagnostic when the server is absent, or keep the current standalone service as an opt-in fallback.

## Recommended release architecture

1. **Publish the NEC runtime as a normal Railyard mod.** It remains manifest `local.nec-corridor-open-world` unless a stable public ID is chosen before release. Railyard's mod installer can extract the bundle; no PowerShell hook is needed or available.
2. **Emit 34 Railyard-compatible map ZIPs**, one per NEC game city code, with the required native city files and PMTiles archive. Add corresponding registry manifests and version feeds/checksums.
3. **Ask Railyard for a collection/map-pack feature or cross-asset dependency.** The desired interaction is “Install Northeast Corridor,” which subscribes the runtime mod and all 34 maps atomically. No such manifest field was found in this installed version.
4. **Add an NEC Railyard mode.** In this mode, wait for Railyard's cities, do not call the current 8799 tile override path, and run only the open-world state/switching logic. Preserve the native PowerShell mode for direct/manual launches.
5. **Add compatibility diagnostics.** Before entering NEC, verify all 34 city codes/data packages are present and that one Railyard tile endpoint responds. Report exactly which assets are missing and tell the user to launch/sync through Railyard.
6. **Test the actual consumer bundle.** Build from `prototype/nec-corridor/mod`, verify a unique Railyard-mode marker in `dist/index.js`, install that consumer, launch through Railyard, and exercise multi-tile transitions. A KC shared-source build is not delivery evidence.

## Feasibility summary

| Goal | Feasibility | Assessment |
| --- | ---: | --- |
| Avoid a user-run PowerShell command when launching through Railyard | High | Railyard already owns a native Go PMTiles server and map extractor. |
| Have the current NEC renderer dynamically register its existing PMTiles with Railyard | Low | No installed cross-process registration/API or dynamic loader extension point exists. |
| Publish NEC as Railyard-native content with current Railyard unchanged | Medium | Technically viable as 34 maps + 1 mod, but awkward to install and requires NEC binding changes. |
| Deliver a one-click NEC package after small Railyard cooperation | Medium-high | A collection/dependency mechanism plus a loader-ready/base-URL contract would close the main gaps. |
| Make direct Subway Builder launches automatically start Railyard from the mod | Very low | The renderer bridge cannot spawn processes or invoke arbitrary IPC. |

Bottom line: **Railyard is the right way to eliminate the PowerShell service for mainstream distribution, but this is a packaging-and-lifecycle integration, not a runtime tile-registration call.** The clean public release needs Railyard to install/serve the map assets and NEC to become a consumer of that service rather than competing with it.
