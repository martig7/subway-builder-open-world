# WebAssembly feasibility for midnight routing

Date: 2026-09-10. Scope: feasibility research; no runtime changes or measured Wasm speedup.

## Findings in this repository

The best initial Wasm candidate is the shared transit search in `open-world-platform`, used by both cross-tile demand and off-tile native-demand estimation. It already runs in workers. The opportunity is reducing object allocation and string-key lookup in a CPU kernel, coupled with reducing repeated work across the complete calculation.

The midnight operation has several stages. Service edits set dirty flags; `flushAtMidnight` calls `recalculateCrossTileModeShare`. That operation captures authoritative state, refreshes the derived network and network profile, calls `refreshNativeCommutes`, compiles native revenue profiles, performs the applicable finance handoff, loads cross demand, evaluates cross-tile choices, and applies results. Native commute refresh can return early or invoke the game's `simulateCommutes`; rewriting the mod's router does not automatically replace that native calculation. The entry point already records an overall `latestCrossModeShare.milliseconds`, but that is not a stage-by-stage profile. Sources: [hook policy](../../open-world-platform/src/runtime/mode-share-hook-policy.js), [runtime](../../open-world-platform/src/runtime/world-tile-runtime.js), [game adapter](../../open-world-platform/src/runtime/adapters/subway-builder-game-adapter.js), [entry point](../../open-world-platform/src/runtime/start-open-world.js).

Concrete optimization candidates, subject to profiling:

| Candidate | Evidence and proposed experiment |
| --- | --- |
| Packed transit-search kernel | `routeLeg` uses Maps for labels and settled states, string station/route keys, heap tuples, and new object labels in `advanceRouteLabel`. Use numeric state/edge IDs, packed adjacency and schedule tables, reusable label/heap buffers, and predecessor indices. Compare packed JavaScript with Rust or C++ compiled to Wasm. |
| Bounded parallel tile evaluation | `#compileNativeFinanceProfile` awaits each stale tile inside its loop; the package adapter uses one shared native-demand evaluator worker. Independent tile computations could use a small worker pool over a fixed network snapshot, with results staged and committed through the existing handoff. Measure memory, duplicate caches, and contention. Cached/unserved tiles already have fast paths, so do not assume all tiles need computation. |
| Retained decoded demand | The native-demand worker inflates and parses supplied bytes on each evaluation request, then fingerprints and normalizes demand. A bounded cache of decoded or packed demand could avoid that repeated work after an edit. Immutable package identity and memory limits must govern retention. |
| Numeric mode-choice loop | `chooseModesFromMetrics` scans a Float64 income array per demand group, comparing affine costs for driving, transit and walking. This is a more regular SIMD candidate than heap traversal. An alternative experiment is sorting the reusable income distribution once and counting exact cost intervals; income generation includes deterministic noise, so the existing array must not be assumed sorted. Preserve ties, floating-point behavior, unavailable-mode values and minimum-transit thresholds. |

Sources: [routing and mode choice](../../open-world-platform/src/runtime/cross-tile-mode-choice.js), [native-demand evaluation](../../open-world-platform/src/runtime/off-tile-native-demand.js), [native-demand worker](../../open-world-platform/src/workers/native-demand-evaluator-worker.js), [package adapter](../../open-world-platform/src/runtime/embedded-tile-package-adapter.js), [runtime tile loop](../../open-world-platform/src/runtime/world-tile-runtime.js).

Off-tile evaluation routes both outward and return demand using the same kernel. Cached simulation also uses this evaluator with assignments enabled and has its own refresh lifecycle; when profiling, record whether cached simulation is enabled and include its refresh if it contributes to the observed delay. Cross-tile fare callbacks are already deduplicated and batched back to the native host. Retain that boundary rather than adding per-edge Wasm-to-JavaScript callbacks. Sources: [off-tile evaluator](../../open-world-platform/src/runtime/off-tile-native-demand.js), [cached simulation](../../open-world-platform/src/runtime/cached-simulation.js), [cross worker](../../open-world-platform/src/workers/cross-mode-share-worker.js).

## What existing measurements establish

The September 7 Japan regional benchmark used 316 stations, 53 routes and 33,553 cross-demand groups. Its live worker medians were 967.5 ms with empty routing caches and 549.9 ms with warm caches. A representative cold pass performed 809,303 edge relaxations; the warm pass performed none. These are historical measurements of cross-network evaluation including transport, fare callbacks and settlement calculation, not a current post-edit midnight profile. The cold/warm difference also includes graph and catchment reuse, so it cannot be attributed entirely to shortest-path search. Sources: [benchmark explanation](../cross-network-routing-performance.md), [raw measurements](../cross-network-routing-japan-benchmark.json).

The same report mentions a separate 12.8-second startup recalculation involving native-demand compilation and native commute refresh. It is not a midnight baseline and must not be used to predict midnight speedup. A topology/service edit in the benchmark's connected network invalidates the affected routing region; unchanged warm-cache runs are therefore insufficient to judge the proposed change. Exact search keys also include departure time. Source: [benchmark explanation](../cross-network-routing-performance.md), [routing cache and keys](../../open-world-platform/src/runtime/cross-tile-mode-choice.js).

For illustration only, if the replaced kernel occupies 50% of the full delay and becomes ten times faster, the total speedup is `1 / (0.5 + 0.5 / 10) = 1.82x`. If it occupies 90%, the same kernel improvement produces `5.26x`. These are arithmetic scenarios, not predictions for this mod.

The historical measured consumer is `local.japan-open-world`, produced by `prototype/japan/mod`, consistent with its current [manifest](../../prototype/japan/mod/manifest.json). This research did not inspect the live renderer or establish which consumer is active now. A future implementation must identify the active runtime first and build/install that consumer from the shared platform. No game bundle was changed or installed during this research.

## Recommended first implementation scope

Instrument one representative topology edit through midnight completion, including native commute refresh, each stale tile's decode/normalization/search/mode-choice time, cross evaluation, host fare calls, and result application. Record CPU profiles in both renderer and workers, cold and repeated runs, allocations, memory peaks, and main-thread stall durations. Then choose the largest measured contributor from the candidates above.

For a Wasm pilot, retain one module and packed graph per worker, pass batches of queries, and return compact journey results. Preserve departure schedules, dwell, access-only driving, transfers, equal-cost route ordering and fare attribution; do not substitute a static-distance shortest-path algorithm. Keep Native Saves and the existing finance handoff authoritative. Validate full results against the JavaScript implementation on actual post-edit snapshots before measuring the selected consumer in game. Sources: [routing semantics](../../open-world-platform/src/runtime/cross-tile-mode-choice.js), [routing regression tests](../../open-world-platform/tests/cross-routing-cache.test.js), [native authority ADR](../adr/0002-native-saves-own-rail-topology.md).

## Findings from primary sources

**Hot JavaScript already runs as machine code.** V8's current architecture describes an interpreter, a baseline compiler, and optimizing compiler tiers that generate machine code for hot functions. Wasm is therefore not a switch from interpreted code to machine code. Its potential advantage must come from a better representation, generated instructions, or execution structure. The actual game's V8 version still needs to be checked; the source describes current V8. [V8 architecture](https://chromium.googlesource.com/v8/v8.git/+/refs/heads/main/docs/overview.md)

**Wasm also has compilation and warmup behavior.** V8 documents baseline compilation with Liftoff and optimization of hot Wasm functions. Debugging can replace optimized Wasm with baseline code, while Performance recording triggers optimization again. Benchmark cold startup, warm repeated calls, and the intended profiling mode separately. [V8 Wasm compilation pipeline](https://v8.dev/docs/wasm-compilation-pipeline)

**The API boundary and memory layout matter.** Emscripten documents direct exported calls, numeric pointers, bulk copying into Wasm memory, and direct typed-array access. Converting strings allocates memory; calling back into JavaScript has overhead. Wasm memory growth can invalidate existing array views. Design inference: keep a packed graph resident in Wasm memory, submit batches of numeric query inputs, and return packed outputs. Avoid a JavaScript callback for every edge or heap operation. Include conversion, copying, result decoding, and allocation in end-to-end measurements. Packing should be measured in JavaScript too, to distinguish representation gains from compiler gains. [Emscripten interoperability](https://emscripten.org/docs/porting/connecting_cpp_and_javascript/Interacting-with-code.html)

**Workers and Wasm solve different parts of the problem.** Google's Wasm guidance demonstrates moving CPU work into a worker and reusing initialization. The HTML Standard describes workers as long-lived, with startup and memory costs, and supports transferring ArrayBuffers instead of cloning them. Inference: worker offload can improve responsiveness without reducing total routing work; parallel independent batches may reduce elapsed time, but copying, initialization, contention, and available cores must be measured. Ordinary workers with private Wasm instances and transferred buffers are an option without shared-memory threads. [Google's Wasm performance patterns](https://web.dev/articles/webassembly-performance-patterns-for-web-apps), [HTML Standard: workers](https://html.spec.whatwg.org/dev/workers.html)

**Shared-memory threading has additional host requirements.** Emscripten pthreads use SharedArrayBuffer and require browser cross-origin isolation through COOP/COEP. Pthreads need compile/link flags and may use a precreated worker pool; threaded and nonthreaded deployment require separate builds. This does not establish that the game's renderer provides those capabilities. Verify the actual Electron/Chromium version, worker creation, Wasm compilation permissions, and `crossOriginIsolated` before choosing this path. These prerequisites apply to shared-memory pthreads, not to basic single-thread Wasm. [Emscripten pthreads](https://emscripten.org/docs/porting/pthreads.html)

**SIMD is selective, not automatic.** Emscripten supports WebAssembly SIMD with `-msimd128`, including compiler vectorization and explicit intrinsics. Its documentation describes portability limitations and operations that require multiple host instructions; 256-bit native operations may be decomposed into 128-bit operations. Design inference: regular contiguous cost calculations or bulk scans are more plausible SIMD targets than branch-dependent priority queues and irregular graph traversal. SIMD should be a later measured experiment, not the initial justification for a routing port. [Emscripten SIMD](https://emscripten.org/docs/porting/simd.html)

## Suggested experiment and decision rule

This is an engineering proposal inferred from those constraints, not a measured result:

1. Capture the full topology-edit-to-midnight-completion interval and split graph preparation, request serialization, routing, response decoding, and finance/result application.
2. Export representative routing snapshots and establish deterministic equivalence checks, including unreachable paths, transfers, equal-cost choices, and outward/return behavior.
3. Compare the existing kernel with a packed-array JavaScript kernel and an equivalent single-thread Wasm kernel on identical inputs. Reuse the graph and scratch buffers across query batches.
4. Measure cold and warm runs, total elapsed time, peak memory, and main-thread stalls. Keep the same query set, route semantics, and diagnostics in every comparison.
5. Consider parallel batches only after identifying independent work and testing the actual host. Evaluate SIMD only for demonstrated regular numerical hotspots.

Adopt Wasm if the complete midnight operation improves enough to justify another toolchain and memory ABI. A faster inner loop alone is insufficient if preparation, repeated graph work, serialization, or result application dominates. No numeric speedup is supported until this comparison runs in the selected consumer and actual game runtime.
